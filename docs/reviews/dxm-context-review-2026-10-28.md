## 场景三：从材料中整理项目背景

给代理的请求：使用 DXM，只读项目材料，整理可补进 AGENTS 的背景，并判断同事提出的“打开付款成功页就将订单改成已支付”是否能直接采用。

材料为合成的订单项目，不来自实际客户：

| 文件 | 提供的信息 |
| --- | --- |
| `AGENTS.md` | 客服查询订单项目；当前只读；支付入口与业务决定的位置。 |
| `docs/payment-decision.md` | 2026-10-20 产品与支付负责人确认：平台确认扣款才算支付成功；成功页只展示进度；按交易号去重，重复通知不能重复发货。旧渠道时间单位为秒，换渠道时重新核对；失败回调的重试次数未确定。 |
| `docs/checks.md` | 2026-10-21 记录本地检查覆盖验签失败和重复交易通知，未覆盖真实渠道或发货服务；没有可复用测试命令。 |

提供的 `src/payment.py`：

```python
def apply_callback(order, payload, verified):
    if not verified:
        raise ValueError("unverified callback")
    if payload["transaction_id"] in order.seen_transactions:
        return order
    order.seen_transactions.add(payload["transaction_id"])
    if payload["status"] == "success":
        order.state = "paid"
    return order
```

实际结果：

- 按已有业务决定拒绝直接采用成功页改状态的建议，解释页面访问不能证明平台已扣款。
- 拟写的项目背景区分业务约定、当前代码、旧渠道约束、待确认重试次数和验证缺口；没有把旧测试记录算成本轮通过，也没有编造测试命令。
- 指出代码只接收 `verified` 参数，不能由此声称实际验签与发货链路已经验证。
- 额外识别出一个条件性风险：若同一交易号先收到非成功通知、再收到成功通知，先写入去重集合可能使后续成功通知被忽略。明确这是取决于渠道语义的推断，未写成已经发生的故障。

观察：本场景保留了影响判断的背景与依据，并能在资料缺失处停止下结论。代理报告只读、未运行测试，材料文件经核对保持原样。
