# DXM 参考

按需读相关的一节。

## 上下文选择

先说清这一步缺的是哪一种：业务目标、历史决定、当前实现、项目进度还是验收依据，然后只找那一种。

检索范围限于用户授权的工作区和已接入的数据源。路径未知时用宿主现有搜索，查询带上项目身份和本次问题。其他仓库、邮箱、用户目录和聊天历史需要用户另行指向。

同一会话内复用已读片段。出现新改动、新证据、目标变化，或结论依赖易变状态（分支、部署、运行中的服务）时，重新核对那一部分。

引用事实时带上来源、适用项目和有效条件。文档可能落后于代码，代码也可能偏离业务意图；看到矛盾就把两边依据摆出来。

## 决策记录

确认过的决定，在获准写入时记到项目已有的合适位置：决定、原因、适用范围、依据。旧决定被替代时标明替代关系；尚未确认的内容标为假设或提议。

跨会话交接只需五项：目标、已做、未做、证据位置、下一步。

业务术语有歧义或取舍需要长期保留时，使用已安装的领域建模技能，否则直接在现有项目文档中处理。

## 验证对照

| 声明 | 需要的证据 |
| --- | --- |
| 缺陷已修复 | 原故障路径复测通过，并检查最可能受影响的相邻分支 |
| 界面已改好 | 实际渲染和被改动的交互 |
| 服务已恢复 | 业务入口的真实请求；端口监听和健康检查只算辅助 |
| 数据已持久化 | 写入后重读；声明涉及恢复时再做重启或失败恢复 |
| 已发布 | 读回版本号、标签和公开产物 |
| 只改了源码 | 写明运行未验证 |

验收目标保持原样：缺环境或权限时，交付可证明的部分并列出缺口。原本就存在的失败与本次引入的失败分开报告。

自身复核如实称为自身复核；独立审查需要真正独立的审查者或项目指定的机制。是否委派、并行多少，由风险和可用工具决定。

## 工作区

高风险或批量修改先准备恢复办法，必要时做范围有限的备份。确认路径的真实归属，留意指向授权范围之外的符号链接。密钥和私有资料留在本地，共享文档与交付说明里只写结论。已有构建产物仍适用就复用，临时输出放在项目约定的忽略目录。
