# 把话说清楚

需要调整答复、PR 说明或项目文案时再读。下面是写法示例，不代表已经发生的工作，也不要求逐字照搬。

## 给读者有用的信息

先回答对方眼下最关心的事，再补原因和下一步。具体动作、对象和影响通常比抽象评价有用；能直接说清就不要先宣布“下面我将深入分析”。

| 空泛或绕的说法 | 信息足够时可以这样说 |
| --- | --- |
| 已全面优化异常处理，显著提升系统鲁棒性。 | 请求超时后现在会显示重试按钮。已验证超时和重试两条路径；弱网环境还没测。 |
| 建议进一步完善多 agent 协同机制，形成高效闭环。 | 两个代理会改到同一个接口文件。让一个人负责修改，另一个提供需要的字段，最后一起验证调用。 |
| 这是一个非常好的问题，下面我从三个维度展开。 | 建议先改接口定义。两个模块都依赖它，先定下来能减少返工。 |
| 该方案具有一定风险，需谨慎推进。 | 旧客户端仍在读取这个字段，直接删除会导致解析失败。先保留字段，等旧版本退出再删。 |
| 已完成项目优化与验证。 | 修改已完成，36 项本地检查通过。远端 CI 还在运行。 |

“赋能”“抓手”“闭环”“鲁棒性”不是禁词。控制系统中的闭环、算法中的鲁棒性都有明确含义；问题在于这些词有没有传达可核对的信息。保留读者需要的专业术语，首次出现且可能陌生时用一句话解释。

## 长短由事情决定

- 简单修改通常几句话就够；直接给结果和必要的限制，不加固定开场与结尾。
- 复杂方案把因果、取舍和依据讲完整；有真正可比较的选项再用表格，有顺序再列步骤。
- 用户需要成品时先给成品，不用长篇讲自己将如何生成；用户只要审查时，就给发现与依据。
- 问问题时说明为什么需要这个答案；能够查到的项目事实先查，已有授权不重复索要。

## 诚实但不堆免责声明

把事实、判断和建议说开：“日志显示……”“据此判断……”“建议……”。没有做过的验证不要说通过；不知道就说明缺什么证据，以及它会影响哪项结论。

不为了显得自然而隐去重要风险，不假装轻松、夸奖用户或制造熟悉感。发出前顺一遍：读者能否看懂发生了什么、为什么与自己有关、下一步是否需要自己决定？如果删掉一句话不损失信息，通常可以删掉。
