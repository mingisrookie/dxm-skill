# 项目知识怎么留

建立项目规则、补充背景或交接长任务时再读。先找已有说明、issue 和决策记录；不为使用本技能新建一套文档体系，也不把所有资料一次性载入。

## 值得留下的内容

优先保留模型无法自己知道、从代码难以看出，或每次都要费力重新查证的信息。

| 内容 | 记录到什么程度 |
| --- | --- |
| 业务含义与限制 | 谁使用、成功是什么、哪些行为会伤害业务，以及原因。 |
| 历史取舍 | 为什么选了当前方案，放弃了什么，什么条件下值得重做。 |
| 导航与验证 | 关键入口、接口定义、真实命令、必要环境和成功的判断方式。 |
| 已知问题与差异 | 问题的触发条件、影响、已证实的处理办法；开发与生产的关键差异。 |
| 当前未知 | 会改变方案的未确认事项、现有线索和需要谁或什么证据确认。 |

不逐文件翻译源码，不复述模型已知的通用知识，不把每次临时处理变成永久规则。保存出处和关键结论，通常比复制整段资料更便于复核。

## 把事实、现状和假设分开

例如，下面是一条假设的订单项目记录：

> 业务约定：只有支付平台确认扣款成功，订单才算已支付。当前实现通过回调更新状态；前端跳回成功页不能作为依据。原因是用户可能在回调前关闭页面。依据：已有支付约定及回调实现。更换支付渠道或结算规则时复核。

“回调代码是这样写的”只能证明当前实现，不能单独证明业务就应该如此。文档、实现和用户要求冲突时，指出冲突并查证；新需求可以改变旧约定，但不能把自己的猜测写成已确认决定。

容易变化的信息留下可定位的来源；核实日期、版本或提交在有助于判断新旧时再记，不要求每句话配一套字段。来源缺失时说明尚未确认，不编造链接、命令或负责人。

## 什么时候更新

接口、环境、业务规则或重要选择变化时，修改原记录；重要决定被替代时保留简短原因和新去向。删除重复、失效或不再影响判断的提醒，避免只加不减。

任务进度与长期事实分开。进度优先留在已有任务记录，长任务交接只需够下一个执行者继续：目标与范围、采用的决定及原因、已完成和未完成、变更或提交位置、实际验证、已知问题和下一步。没有写入授权时直接在对话中交接。

## 项目更新日志

有现成 changelog 就沿用；项目约定用 Release notes 或其他记录时也沿用。需要新建时先确认属于本次维护范围。记录使用者能感知的变化：行为、接口、默认设置、重要约定、兼容或迁移影响，不记录每次提问、工具调用和代理工作流水账。

开发中的变化先写在未发布区域。以下是格式示例，删去空项，不把示例当成本次记录：

```markdown
## Unreleased（未发布）

### 变更

- <具体改变了什么，使用者会有什么不同>

### 兼容与迁移

- <是否需要调整配置、更新安装副本或改变调用方式；无影响可省略>
```

正式发版时再按项目惯例确定版本和日期，并同步版本文件与发布说明。changelog 是变更记录，不能证明测试通过或版本已发布；验证结果和发布结果应以真实执行为准。
